Slack OAuth install design — class & sequence

Static design for adding a one-click "Add to Slack" install flow, co-located inside the existing slack_handler Lambda via path dispatch. Companion to the implementation plan at ~/.claude/plans/misty-snuggling-panda.md and the option-space exploration at .claude/research/2026-05-04-slack-oauth-callback-url.md.

Goal

Today: single-tenant. One SLACK_BOT_TOKEN in Doppler, hard-bound to one workspace.
Goal: any workspace admin can click "Add to Slack" and have their workspace's bot_token delivered straight from Slack to our backend (via OAuth v2), persisted, and ready to use — without the admin ever copy-pasting a token.

Scope of this design is the install (write) path only: acquire and store the per-workspace bot_token. The read-path refactor (making the app_mention handler look up the token by team_id instead of reading the env var) is an explicit follow-up; until it lands, the existing single-tenant event handler keeps running unchanged.

What to take from the class view. Three new modules (NEW slack_oauth.py, NEW slack_installations_repository.py, NEW slack_installations table) plus one tiny edit to MODIFIED slack_handler.py (path dispatch ~10 lines) and MODIFIED table_names.py (one constant). Existing slack_bot.py and aurora/client.py are UNCHANGED. The dotted edge from SlackBot to the repository is what the follow-up spec will wire up — calling out the gap explicitly so the architecture diagram doesn't lie.

Module responsibilities at a glance

ModuleStatusSingle responsibilityKey invariants
slack_handler.py MODIFIED HTTP-method & path dispatch only. Lazy-imports concrete handlers. Returns 404 for unknown paths. Events-path env-var check stays scoped to the events branch.
slack_oauth.py NEW Validate state, exchange code, persist install. No events logic ever crosses this boundary. Token never logged. State HMAC verifies origin.
slack_installations_repository.py NEW UPSERT and lookup by team_id. Idempotent on re-install (ON DUPLICATE KEY UPDATE). No business logic.
slack_bot.py UNCHANGED Single-tenant event dispatch + Slack API calls. Still reads SLACK_BOT_TOKEN env var. Will become tenant-aware in follow-up.
aurora/client.py UNCHANGED Shared pymysql connection pool. Reused exactly as user_repository.py uses it.

Where workspace identity enters. Step 2 inside the orange box. Slack's web UI is where the admin picks the workspace; the choice rides as internal Slack state keyed by the one-time code. Our backend learns team_id only at step 14, when it exchanges the code via oauth.v2.access. No URL the user clicks contains a team_id parameter — and intentionally so: a URL parameter would be forgeable, whereas the code is unforgeable because only Slack can mint it.

Follow-up (NOT in this design)

The dotted line in the class diagram (SlackBot ..> SlackInstallationsRepository) is the next spec:

  • Refactor SlackBot.__init__ to accept bot_token as a constructor argument.
  • Refactor handle_webhook to extract team_id from the event payload and look up the per-workspace token via get_token_by_team_id(team_id).
  • Backfill the existing single-tenant install into slack_installations as a one-row INSERT before cutover.
  • Remove SLACK_BOT_TOKEN from Doppler + Lambda env vars.
  • Subscribe to app_uninstalled events; delete the row when a workspace removes the bot.
