Reconciliation — /tf-aws does NOT auto-resolve DRIFTED items (resolving mutates AWS, which is terraform apply territory and a deliberate change-management event):

  • apply-tf — TF declaration wins; push to AWS via terraform apply. Use when TF reflects the deliberate spec.
  • refresh-tf — AWS reality wins; pull into state via terraform refresh then commit. Use for AWS-authoritative fields like Lambda code_sha256.
  • review — read CloudTrail to learn who changed what when, then pick a direction. D1 is here because the direction is unrecoverable from a single snapshot.

Blind spots and limits — what ✅ doesn't prove

The two-axis δ above measures agreement between TF state and AWS reality on the fields the audit can see. It does not measure correctness in any broader sense. This panel names the four structural categories of things /tf-aws audit cannot discover, and pairs each with a "plug" — a cheap mitigation that lives outside the audit. Source: .claude/commands/tf-aws.md § "Blind spots and limits". Companion journal: .claude/journals/architecture/2026-04-28-tf-aws-blind-spots-documented.md.

#CategoryWhat ✅ on the audit doesn't provePlug (mitigation outside the audit)Components affected in this run
BS-1 Layer-coverage
config-level vs runtime		 That a TF-tracked Lambda actually works at runtime. The audit reads its declared config and live config on a fixed projection of fields; it never invokes the Lambda. "LINE bot working" is a config-level smoke for a small subset of Lambdas — it does not exercise the imports listed below. CloudWatch error rate + Level-1 smoke (per-Lambda aws lambda invoke with a known-good event) + Level-0 e2e (real user flow). Run after every import. WebhookHealth (item #1) · ModelCatalog (item #2) · QuantAgent (item #3)
Once imported, all three pass the membership audit (✅ TRACKED). None has a runtime smoke covering it.
BS-2 Post-action amnesia
verbs that erase intent		 Why a resource was in the disagreement set before reconciliation. Verbs like terraform state rm, terraform refresh, and trim-spec collapse the spec onto reality and leave the TF state with no record of the original finding. Future audits won't re-flag what is now absent on both sides. Journal the decision before running the destructive verb (Plug #2). Capture: original finding, why we accept reality, and the conditions that would re-open the decision. TgLambda (D1 trim-spec pending — see terraform/telegram_api.tf:149 + src/telegram_lambda_handler.py:80) · Aurora (Aurora SG rules state rm pending — aws_security_group_rule.aurora_from_codebuild, aurora_from_proxy from validation 2026-04-27)
Once executed, both findings disappear from future audits. Companion journals must exist before the verbs run.
BS-3 Field-coverage
drift on undeclared fields		 Drift on any field not listed in projection.fingerprint_fields for the resource type. Phase C2 only diffs the named projection. A new env var, a tag change, a reserved_concurrent_executions bump — none surface as DRIFTED if the field isn't in the projection. Treat projection.fingerprint_fields in .claude/replicas/dr-bot.yaml as a living list. Extend it after every incident where a field should have been caught and wasn't. Cannot enumerate exhaustively by design, but examples (truly outside the audit's reach today): on aws_lambda_function — tags, timeout, memory_size, layers, reserved_concurrent_executions, tracing_config, dead_letter_config; on aws_rds_cluster — backup_retention_period, deletion_protection; on aws_security_group — tags, description; on aws_apigatewayv2_api — tags, cors_configuration. Not BS-3: IAM policy attachments, SG rules, Lambda event source mappings — these are their own TF resource types and are caught by δ_membership when in y.filter. Audited as ✅ today on the projection, but invisible to drift on the fields above.
BS-4 Scope-coverage
resources outside the filter		 The existence and state of any AWS resource that doesn't match the replica's y.filter predicates. Resources outside the filter do not exist to the audit — they are neither tracked nor flagged. Periodic unscoped sweep — list all resources of the in-scope types in the region+account, subtract the filter, manually review the remainder. Catches both "should have been in scope" and "is silently consuming budget". Cannot enumerate from inside this report — by definition, the list lives outside the filter. Known suspects from prior validations: KMS keys, log groups outside the dr-* name pattern, IAM users/roles not tagged with the project tag.

Reading order for a passing audit (what to combine with ✅ before claiming "system healthy"):

δ_membership = 0   AND   δ_config = 0
                 AND   BS-1 plug ran:   per-Lambda runtime smoke for the imports
                 AND   BS-2 plug ran:   Plug #2 journals exist for every state-rm / trim-spec / refresh
                 AND   BS-3 plug ran:   projection.fingerprint_fields reviewed against last incident
                 AND   BS-4 plug ran:   unscoped sweep within the last review cycle
=========================================================
                 ⇒  "system healthy" (within audit's epistemic surface + named plugs)

Why this section exists in this report: the reconciliation plan in "Recommended next steps" runs two destructive verbs (state rm and trim-spec) and imports three Lambdas not exercised by the LINE smoke test. Without this section, an agent reading the report after reconciliation would see ✅ everywhere and conclude the system is healthy. ✅ has a narrow technical meaning here — it means "TF and AWS agree on the fields the projection diffs". The plugs above are what make ✅ load-bearing for the broader claim.
