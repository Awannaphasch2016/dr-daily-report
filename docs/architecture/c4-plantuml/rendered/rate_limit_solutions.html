Rate-limit solutions — mental framework

2026-05-03 · scope: dev precompute pipeline · 8 candidates organized into 3 zones

The reframe

Stop thinking of this as "yfinance is flaky." Think of it as burst pressure flowing through a 3-segment pipe: 46 workers (source) → one shared NAT IP (pipe) → Yahoo's per-IP rate limit (sink). Every fix lands in exactly one of those three zones, and the zone tells you the trade-off shape before you read any details.

Source · the 46 workers

Lever: control how many calls leave per second.
Cost shape: code only, near-zero $/mo.
Ceiling: at best mitigates — Yahoo limit still applies.

Pipe · the shared NAT IP

Lever: get more egress IPs.
Cost shape: AWS infra, $$/mo per extra IP.
Ceiling: linear gain (more IPs = more budget).

Sink · Yahoo's per-IP limit

Lever: avoid the call (cache) or replace the service (paid feed).
Cost shape: build effort or recurring $.
Ceiling: removes the dependency entirely.

Recommended path

Step A — today, ~30 min: ship #1 + #2 together.
One value change in precompute_workflow.json (MaxConcurrency 46→8) and one code change in data_fetcher.py (jittered exponential backoff). Buys 56/56 most mornings while the structural fix is built.

Step B — this sprint, ~3 days: build #3 (single-writer price cache).
One scheduled Lambda fetches each ticker once per day from Yahoo, writes to daily_prices /daily_indicators. Report-workers read those tables instead of calling Yahoo. Removes the rate-limit dependency from the precompute path entirely. Same architectural shape as the A4 RDS-Proxy fix in the PDF GORE — solving once helps both problems.

Skip: #7 (proxy pool) — Yahoo ToS forbids; account-ban risk.
Defer: #4 (NAT-per-AZ) — useful defense-in-depth, but #3 makes it unnecessary. Revisit only if other Yahoo-callers start tripping the same limit.

Why not just jump straight to the structural fix (#3)?

  1. Buys observation time. Once burst pressure is reduced (#1+#2), you can measure the true baseline failure rate. If it drops to 0, you may not need #3 at all.
  2. Validates the diagnosis. If lowering concurrency doesn't help, the bottleneck isn't per-IP throttling — and #3 wouldn't help either. Cheap diagnostic.
  3. Coverage now, not in 3 days. Every morning the system ships at 42/56 while you're building #3. #1+#2 close the gap in 30 minutes.
